# Перевірка EANyra — 24 жовтня 2026

Перевірено основні шляхи MCP, orchestrator, конфігурацію акаунтів, Telegram-збір,
SQLite schema/repositories та наявні тести. Це локальний аудит коду; реальні
Telegram/X-сесії та повноту історичного скрапінгу не перевірено. Наявні до роботи
незакомічені зміни збережено; робочу базу не мігровано. Після уточнення користувача
в локальний конфіг додано `eclipsisaureum` для збору й дозволеного постингу.
Реальних повідомлень не надсилали. Локальні Telegram API/session/bot credentials
на момент перевірки відсутні, тому live-підключення залишається неналаштованим.

## Виправлено

| Проблема | Зміна |
|---|---|
| MCP міг лише читати раніше зібрані дані | `scraper_run` і `scraper_job_get`; окремий worker, вибір платформи/акаунта |
| Telegram-постинг та визначення бота були відсутні | Bot API gateway, `telegram_publisher_info`, allowlist каналів і durable outbox prepare/publish/get; опціональний явний MTProto transport |
| Telegram-пересилання та відповіді приховувалися типовим posts-фільтром | `telegram_messages_get` без цих виключень, із cursor за DB ID |
| Username був глобально унікальним | Composite key `(platform, username)`, міграція зі збереженням зв'язків, platform-aware sync |
| Невалідний конфіг міг частково оновити акаунти | Повна перевірка структури, платформ, boolean-полів та дублікатів до запису |
| CLI/cron/MCP могли одночасно відкрити один browser profile | Файлове блокування на одну базу даних |
| Помилка до початку account loop залишала run у `running` | Верхній обробник завершує run як failed і звільняє lock |
| Один McpServer повторно використовувався для HTTP transport-сесій | Окремий сервер для кожної сесії; невідома сесія відхиляється |
| HTTP не мав автентифікації, а MCP отримав можливість запускати збір | Loopback-only, перевірка Host та відхилення browser Origin |
| MCP губив помилки відкриття DB через process.exit | Помилка інструмента без зупинки сервера; busy timeout та закриття DB |
| MCP із чужої робочої папки не знаходив правильний .env | Окремий `start.js` launcher із робочою папкою проєкту |
| `posts_get: sample` використовував неправильні aliases у вкладених фільтрах і міг перевищити limit | Виправлені aliases та кінцевий LIMIT |

## Залишені пріоритети

1. **Telegram pagination/backfill.** `TelegramScraper.#fetchMessagesSince` має
   ліміт сторінок. Якщо канал накопичив більше повідомлень, ніж вміщує цей ліміт,
   orchestrator просуває baseline після отримання новішої частини історії.
   Старіший непрочитаний проміжок може бути пропущений. Потрібен окремий
   збережений pagination cursor і явний статус неповного збору.
2. **Життєвий цикл після аварії.** Hard kill залишає lock/run; автоматичне
   відновлення має перевіряти власника й heartbeat, щоб не розблокувати активну
   сесію. Job history зараз у пам'яті, а не в durable queue.
3. **Ізоляція брендів.** Кілька джерел уже підтримуються, але Telegram login,
   Twitter browser profile і YAML voice/bio залишаються спільними. Для ведення
   різних брендів потрібні окремі identity/session/context, а не лише ще один
   рядок accounts.json.
4. **GitHub README baseline.** Перший SHA не зберігається як окремий checkpoint;
   поточна перевірка змін покладається на попередні readme_change signals.
5. **LinkedIn multi-account.** Всі профілі читають один Shares.csv. Потрібна
   прив'язка файлу імпорту до акаунта, інакше перший профіль забирає його записи.
6. **Точність scraper_status.** Поточний data_age_hours походить від останнього
   завершеного run, навіть якщо він failed; потрібна дата успішного збору для
   кожного джерела. posts_saved також включає GitHub signals.
7. **Remote MCP та scheduling.** Віддалений доступ наразі навмисно недоступний;
   для нього потрібні auth, session expiry і request budgets. Twitter-збір
   послідовний із паузами 5–15 хвилин між профілями за типовими налаштуваннями.
   При більшій кількості профілів потрібні окремі розклади платформ і черга.

## Перевірки

Після наступного рефакторингу акаунти, YAML-контекст, браузерний профіль та база
переміщені в `instance/`; `.env` залишається в корені репозиторію. Хеші семи основних файлів (акаунти,
контекст, база, cookie cache) до й після перенесення збігаються; непов'язані зі
шляхами значення `.env` збережені. Шаблони тепер у `instance_example/`.
Правила нового розташування: [INSTANCE_GUIDE.md](INSTANCE_GUIDE.md).

- Початкова suite: 20/20 тестів.
- Після змін: 54/54 тести; `node --check` для змінених JS-файлів та
  `git diff --check` проходять.
- Додано unit-перевірки account validation/sync, migration, lock, jobs та MCP schemas.
- Перевірено init без перезапису, перенесення legacy-файлів зі збереженням
  вмісту, конфлікти й locks, незалежність шляхів від cwd та ізоляцію інстансів.
- Робоча SQLite після перенесення пройшла read-only `PRAGMA integrity_check`.
- Окремий виклик `tools/list` до реального локального MCP підтвердив реєстрацію
  методів читання, публікації й запуску збору без виконання цих дій.
- Додано QR-вхід за прикладом локального Inemuri: перевірено оновлення QR,
  2FA без відображення пароля, phone fallback, скасування, cleanup та запис сесії
  в кореневий `.env` зі збереженням решти налаштувань. Telegram у цих тестах
  замінений тестовим клієнтом; реальний вхід потребує сканування з телефона.
- Інтеграційний MCP stdio-клієнт перевіряє читання Telegram, pagination,
  platform/account filtering, валідацію й справжній worker на порожньому конфігу.
- Два незалежні HTTP-клієнти перевіряють sessions, unknown session та Origin.
- Перевірено durable Telegram draft після перезапуску MCP, перевірку bot setup,
  allowlist/admin rights, точний plain text, конкурентне надсилання, повторний
  request_id, невизначену доставку та приховування токена в помилках. Відправлення
  і відповіді Telegram API у цих перевірках замінені тестовими реалізаціями.
- Усі інтеграційні дані зберігаються у тимчасових SQLite-файлах, реальний збір
  мережевих джерел під час тестів не виконується.

Підключення та приклади: [MCP_GUIDE.md](MCP_GUIDE.md).
